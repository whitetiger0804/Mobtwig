# 회원 가입·세션 계약 · #19 / #20

2026-11-07 사용자 확정. 이메일·닉네임으로 가입하고 이메일로 로그인한다. 가입 성공 후 로그인 화면으로 이동한다. 일반 회원 비밀번호는 영문·숫자를 포함한 8자 이상이며 BCrypt 입력은 UTF-8 최대 72바이트다. 개발·시연용 임시 문서 두 종류를 사용한다.

## 요청 계약

| 요청 | 입력·응답 | 오류 |
| --- | --- | --- |
| `GET /api/auth/csrf` | 현재 회원 세션의 `headerName`, `parameterName`, `token` | 잘못된 인증 영역의 쿠키는 401 |
| `GET /api/auth/terms` | 현재 이용약관·개인정보 수집·이용 동의의 버전·해시와 원문 | 503 시연 가입 꺼짐 |
| `POST /api/auth/signup` | JSON `email`, `nickname`, `password`, `passwordConfirmation`, `consents`. 성공 201에 `id`, `email`, `nickname` | 400 필드 오류, 403 CSRF, 409 중복·구버전 문서, 503 시연 가입 꺼짐 |
| `POST /api/auth/login` | 폼 `email`, `password`. CSRF 필요. 성공 204이며 본문 없음 | 계정 부재·비밀번호 오류·비활성은 같은 401, CSRF는 403 |
| `GET /api/auth/session` | 로그인한 활성 회원의 `id`, `email`, `nickname`, `createdAt` | 미인증·만료·활성 상태 상실은 401 |
| `POST /api/auth/logout` | 현재 세션 CSRF. 성공 204이며 회원 세션 무효화 | CSRF는 403 |

가입 요청에 역할·상태·회원 ID를 받지 않고 서버에서 `USER`·`ACTIVE`를 사용한다. 다른 회원 ID로 조회하는 세션 API는 만들지 않는다. 이메일은 입력 공백·대소문자를 정리하고 도메인의 점을 검사한다. 닉네임은 기존 UNIQUE·최대 30자 규칙을 사용한다. 비밀번호는 자르거나 정규화하지 않고 해시로만 저장한다. 가입 시 기본 읽기 설정 생성과 동의 기록은 같은 트랜잭션으로 처리한다.

## 인증 영역 분리

담당자 검토로 기존 관리자 `SESSION` 쿠키와 회원 `MEMBER_SESSION` 쿠키를 분리한다. 관리자 경로는 기존 쿠키를 그대로 사용하고, `/api/auth/**`·`/api/members/**`는 회원 쿠키만 읽는다. 회원 쿠키 Path는 `/api`, 관리자 쿠키 Path는 기존 `/`이다. 모두 host-only·HttpOnly·SameSite=Strict이며 운영의 `SESSION_COOKIE_SECURE=true`를 따른다.

Spring Session JDBC와 비활동 30분 만료는 재사용한다. CSRF 익명 세션부터 `MOBTWIG_AUTH_SCOPE`에 영역을 표시한다. 쿠키 이름만 바꿔 다른 영역의 ID를 전달하면 401과 잘못 제시한 쿠키의 만료만 반환하고 원래 영역의 세션을 무효화하지 않는다. 영역 표시가 없는 기존 인증 세션은 관리자 영역에서만 호환하며 회원 영역에는 사용하지 않는다. 로그인 성공은 세션 ID를 교체하고 CSRF를 새로 받는다.

회원 로그아웃·계정 전환은 회원 세션만 폐기하고 같은 브라우저의 관리자 로그인은 유지한다. 반대 방향도 같다. 일반 회원 세션이 관리자 API에 접근할 수 없으며 관리자 계정의 회원 앱 로그인도 별도 회원 영역 세션이다. 관리자 API는 기존과 같이 요청마다 현재 ADMIN 권한·활성 상태를 검사한다. 회원 API도 DB의 현재 활성 상태를 검사한다.

## 웹과 네이티브

`AUTH_ALLOWED_ORIGINS`에는 정확한 `scheme://host[:port]` origin을 쉼표로 지정한다. 기본은 빈 목록으로 인증 CORS를 열지 않는다. 허용 출처만 credential CORS를 사용하며 와일드카드는 허용하지 않는다. 클라이언트는 `credentials: include`를 사용한다. SameSite=Strict이므로 웹 앱/API는 same-site 배포가 지원 대상이다. CORS 허용만으로 cross-site 쿠키 전송이 가능하다고 간주하거나 SameSite=None으로 완화하지 않는다.

네이티브는 플랫폼 쿠키 저장소를 사용하고 JS·일반 저장소에 세션 쿠키를 직접 저장하지 않는다. 서버 선택을 바꾸면 인증 클라이언트를 새로 만들고 전 회원 상태를 버린다. React Native의 쿠키 인증에는 알려진 제약이 있으므로 실제 Android/iOS의 로그인·CSRF·쿠키 갱신·만료 검사는 번들 생성과 구분한다. [공식 네트워크 문서](https://reactnative.dev/docs/network)

회원 상태 조회·로그인·로그아웃·계정 전환에 세대 번호와 요청 취소를 적용한다. 이전 요청의 늦은 성공/401이 새 계정 상태를 덮어쓰지 않도록 한다. 인증 정보 상실 시 회원 화면·대기 요청·메모리 캐시·내비게이션을 초기화한다. 이번 작업에서 아직 존재하지 않는 서재·독서 기록 API를 임의 추가하지 않는다.

## 약관과 작업 순서

약관은 서버의 버전별 UTF-8 파일에서 읽는다. 화면은 LF로 통일한 원문을 표시하며, 같은 원문의 SHA-256을 문서 버전과 함께 전송한다. 서버는 현재 원문과 일치할 때만 회원·기본 읽기 설정과 동의 원문·해시·서버 시각을 V7 테이블에 함께 저장한다. 시연 가입은 `SIGNUP_DEMO_ENABLED=true`로 활성화한다. 기본값은 false다.

#19 브랜치는 #20의 PR #95에 있는 회원 쿠키·CSRF·로그인 화면을 기반으로 한다. 실제 약관 발행, 이력 보존 정책과 재동의 절차는 [#96](https://github.com/whitetiger0804/Mobtwig/issues/96)에서 다룬다. 실DB 변경 테스트는 전용 테스트 DB와 CI에서 실행한다.
